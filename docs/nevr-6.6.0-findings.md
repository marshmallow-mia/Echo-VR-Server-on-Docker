# nevr-runtime v6.6.0 on Linux: tested behaviour

Measured on 2026-10-30 on the same Debian 12 LXC as [the 5.4.2 notes](nevr-5.4.2-findings.md), game build
34.4.631547.1, release `v6.6.0` (`nevr-runtime-v6.6.0-windows.zip`, sha256
`5df7a4129910d5ed04843a521c74f9935c1b4e66c40c21e6889a140923b565b8`; host `BugSplat64.dll` `09be5c6e…7233`, runtime
`nevr-runtime.dll` `f4312399…516f`, both matching the zip's `SHA256SUMS`). The logs these notes are based on are in
`pkg/supervisor/testdata/v6.6.0-*` (account data removed).

| Topic | Result | What the tooling does |
|---|---|---|
| Package | From v6.0.0 a release has only `nevr-runtime-<tag>-windows.zip`: the host `BugSplat64.dll`, the signed `nevr-runtime.dll`, `echovr_server.exe`, `install.ps1`, `nevr-install.exe`, `SHA256SUMS`. v5.5.0 to v5.20.0 also have only that zip. | From v6.0.0 the `-windows.zip` is the server package; 5.5–5.20 stay unoffered. The store keeps both DLLs and checks every file against `SHA256SUMS`. |
| Layout | The host beside `echovr.exe` loads the runtime only from the nEVR root, `%LOCALAPPDATA%\nevr\echovr` (in the prefix: `drive_c/users/container/AppData/Local/nevr/echovr`). Without it, or when it refuses the signature, the host prints one `{"tag":"NEVR.STOP",…,"code":78,"reason":"runtime_refused",…}` line and exits with **78**, on every start. | Before each start the runtime is copied into the root (only when its bytes changed). Exit 78 and the `NEVR.STOP` line mean `runtime_refused`: failed, not restarted in a loop. |
| Wine | Debian `wine 10.0~repack-6`: the host refuses the runtime, `verify_reason="malformed signature: does not parse as PKCS#7: error 2147942487"` (crypt32 `CryptMsgUpdate`). WineHQ `wine-devel 11.19` (the version nevr-runtime's ADR 0010 measured the check on): accepted, the runtime starts. 11.19 also boots 5.4.3 (it gets as far as the same login as on Wine 10); the WineHQ 11.0 crash of the 5.4.2 notes does not happen. | The image uses WineHQ 11.19, 64-bit half only (`wine-devel-amd64` plus `wine-devel` unpacked; its package depends on the i386 half). |
| Config | `config.yaml` is read from the root (`[NEVR.CONFIG] config.yaml loaded from: C:\users\container\AppData\Local\nevr\echovr\config.yaml chosen_by=nevr root`), or from `-config-file`. `_local/config.yaml` is never read; when the root has none, the first one found is copied there once. EchoVRCE's socket and HTTP addresses and the public HTTP key are built in (`[NEVR.CONFIG] built-in defaults in use … nevr_http_key, nevr_http_uri, nevr_server_key, nevr_socket_uri`). | The root gets its own `config.yaml` with no `services` and no HTTP endpoints (the `NEVR_*_URI` / `NEVR_HTTP_KEY` variables stay overrides); a stale `_local/config.yaml` is removed. 5.x keeps its file. |
| Sign-in | A server's bridge login needs `identity.discord_id` **and** `auth.password` (nevr-runtime #1339). With only a device link (a refresh token in the root's `.credentials.json`) it stops at once: `[NEVR.FATAL] server login refused: no credential configured (missing auth.password)`. The refresh token is still used for the ServerDB token. The release README's "a refresh token when it has one" is older than that rule. | Without `NEVR_PASSWORD` a 6.x runtime is not started: the instance fails with `invalid_config` and the reason. `_local`'s device link is copied into the root once; after that the runtime rotates the root's copy. |
| Console | The runtime's lines still reach the process's stdout/stderr under Wine, as with 5.4.2. | Unchanged: the supervisor parses the console. |
| Not measured | A 6.6.0 login and registration against EchoVRCE: the host account had no password at the time. | |
